# MCP Dev Hub — 상위 제약 (Constraints)

**최종 목표:** 모바일 등에서 개발을 지시한 뒤 WSL Worker가 사전 승인된 범위의 코드 수정 → 격리 테스트 → 실제 독립 Codex 리뷰 → PR/필수 CI → 보호 규칙에 따른 병합 → main CI → Issue Close까지 **사용자 중간 개입 없이** 수행한다. 접속이 끊겨도 상태를 보존하고 이어서 처리한다.

이 문서에는 **프로젝트 전체의 방향·제약·이슈별 책임만 기록**한다. 개별 오류·환경 진단·증거·수정 내역·검증 및 해제 조건은 **담당 GitHub Issues/PRs**에서 관리한다.

## 상위 원칙

1. **WSL Worker가 실행 주체다.** Microduck MCP와 ClosePaw MCP는 선택적인 접속/관찰 수단이며, 특정 경로의 장애가 다른 경로의 개발·CI를 불필요하게 막아서는 안 된다.
2. **승인 범위 내 반복 사용자 개입 0회**가 목표다. 작업마다 sudo나 수동 설치를 요구하지 않되, 새로운 root 정책·허용 범위·신뢰키 변경을 AI가 독단적으로 승인하지 않는다.
3. **보안 게이트를 유지한다.** 최소 권한, 격리 실행, 실제 독립 Codex 리뷰, 필수 GitHub CI 및 branch 보호를 우회하지 않는다. 전역 AI_WRITE/AI_PUSH를 검증 없이 활성화하지 않는다.
4. **데이터와 실행 결과를 보존한다.** 기존 Worker/Dashboard·작업 원장·설정을 보존하고, unknown/timeout 결과는 식별자로 조회한다. 실패한 외부 작업을 추측해 재실행하지 않는다. 미검증을 성공으로 표시하거나 이슈를 조기 Close하지 않는다.
5. **기존 자산을 재사용한다.** 이미 검증한 코드·연결·CI·증거를 우선 활용하고 새 계정/앱/권한 확대나 반복 구축을 최소화한다.
6. **공개 정보는 비식별로 유지한다.** 실제 장비·계정·IP·개인 경로·SSH 구성·키·토큰·운영 로그는 기록하지 않는다. 위험 작업 전에는 담당 이슈의 최신 증거만 필요한 범위에서 재검증한다.

## 보호된 root 업데이트의 프로젝트 기본 정책 — C안 (설계 기준)

**기본 방향:** #35와 이후 보호 파일 변경에는 Galaxy·PC·root에 별도 외부 서명 앱·기기를 필수로 늘리지 않고, **WSL 내부의 서로 분리된 보호 서명 주체**를 이용한다. 별도의 기기 서명 인프라는 기본 전제에서 제외하지만, 실제 PC·Galaxy·private-SSE·root 보안 및 원본 복구 검증은 설치 후에도 수행한다. 상세 신뢰 경계와 완료 조건은 [보호 업데이트 공통 정책](protected-update-baseline.md)을 따른다.

- **역할 독립성:** 일반 개발 Worker는 코드 제안만 수행한다. 실제 정확한 HEAD/BASE Codex 감사를 완료·검증하는 고정 보호 실행기, 별도 OS 사용자에게 귀속된 검토자와 승인자 등 **3개의 서로 다른 Ed25519 서명 주체**가 필요하다. 일반 Worker·원격 제어 셸에 개인키가 노출되거나 Worker가 자신을 독립 검증자로 승인해서는 안 된다.
- **증거와 권한:** 원본 보호 파일·고정 패키지 다이제스트, GitHub의 실제 PR/CI/branch 보호 상태, 유효기간과 재사용 방지, 별도 서명 두 건을 root가 독립 검증한다. 사용자 인증을 동반한 최소 권한 최초 설치 1회만 허용하고, 이후 허가된 업데이트마다 sudo 입력을 요구하지 않는다. root의 고정 두 파일 허용 목록·원자적 교체·CAS·롤백·UNKNOWN 보존은 유지한다.
- **승인 단순화의 한계:** 저장소의 실제 GitHub 보호 규칙은 우회하지 않는다. 기존 내부 GitHub App 승인·외부 영수증 의존성을 제거하려면 **그 전체 실행 경로를 대체하는 보호 검증자를 구현·테스트·독립 감사**해야 한다. 다른 경로의 검사 몇 줄만 삭제하는 것은 허용하지 않는다.
- **현재 적용 상태:** 이 항목은 승인된 **설계 기본 사항**이며 실제 운영 설치 완료 선언이 아니다. #35의 새 검증 계약은 아직 소스 전용이고 기존 부트스트랩·업데이트 실행기가 C안으로 완전히 이행되지 않았다. 따라서 현재 기존 보안 게이트는 그대로 차단/강제하며, 운영 설치·업데이트·종료는 NO-GO다. 실제 진척과 승인 여부는 #35/PR #39의 최신 증거로 판단한다.

## 기본 역할 분담 및 실행 경로 (모든 MCP/SSH 작업)

| 경로 / 주체 | 기본 책임 | 사용하지 않는 경우 |
| --- | --- | --- |
| GitHub 도구/API | 저장소 파일·Issue·PR·리뷰·CI·커밋 SHA·검증 증거 직접 조회/관리. 서로 다른 작업 공간의 단일 변경 기준 | GitHub 작업을 위해 불필요하게 모바일·SSH·WSL을 경유하지 않는다 |
| Microduck MCP | **일반 개발 우선 경로**: 허용된 작업 공간에서 코드 조사·수정·일반 테스트·명시적으로 승인된 에이전트 간 분담 | 실제 호스트 보호 권한, root 설치, 독립 운영 서명/승인 발행을 대신하지 않는다 |
| ClosePaw → SSH → WSL | **현장 작업 전용 경로**: 실제 노트북/WSL 상태, 보호 설치·실행, 신뢰 경계·서비스, 복구·롤백 및 실운영 E2E 검증 | 단순 코드 변경, 일반 GitHub 조회, 중복 연결 확인에 사용하지 않는다 |
| WSL Worker | 기존 설계대로 무인 보호 업데이트와 운영 실행의 최종 주체. 독립 Codex 검증·현재 코드에서 강제하는 승인 게이트(또는 완전히 검증된 보호 서명 대체 경로) 및 최소 권한 준수 | Microduck 도구 사용 자체로 운영 검증·승인 완료를 간주하지 않는다 |

**라우팅 순서:** 작업의 성격과 도구의 실제 지원 범위를 먼저 파악한다 → GitHub 고유 작업은 GitHub에서 직접 처리한다 → 일반 개발은 Microduck을 우선 사용한다 → WSL/호스트·보호 권한에 종속된 단계만 ClosePaw 경로를 쓴다. 필요한 경로가 이미 검증되었으면 다시 구축하지 않는다. 장애 발생 시 다른 독립 작업은 계속하되, 미승인 환경으로 자동 우회하거나 SSH 실패 후 로컬에서 명령을 실행하지 않는다.

**작업 공간 인계:** Microduck과 WSL이 같은 파일 시스템이라고 가정하지 않는다. Issue/PR과 정확한 커밋 SHA를 공통 기준으로 삼고, 별도 작업 트리와 한 번에 한 작성자 원칙을 지킨다. 소스 테스트 통과와 실제 서명·운영 승인·업데이트 수용은 별도 게이트다. 사용자 개입 0회 목표는 유지하되 새로운 root 신뢰/권한 정책에 대한 명시적 승인 요구를 없애지 않는다.
